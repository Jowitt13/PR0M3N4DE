# Student Workflow Routing

The student pre-design workflow runs one confirmed gate after another. Each
stage below is a separately reviewed contract with its own reference,
schemas, and deterministic scripts. Enter only at the stage that matches the
current confirmed state, run the named gates in order, and never skip a
confirmation. These scripts validate, trace, and project what the student or
human has written; they perform no automated design.

## Assignment Brief Ingestion

For a dense assignment brief supplied as files, run the literal brief gate before the numbered route: read [assignment-brief-ingestion.md](assignment-brief-ingestion.md), author the structured intake record (file inventory, pre-extracted segments with source locators, readability, declared conflicts and unknowns), and run `scripts/build_assignment_brief_digest.py build <intake.json> --output <digest.json>`. This gate parses no DOC, DOCX, PDF, HTML, or image content and claims no format extraction support; it emits a literal-only digest that keeps a source locator and one coverage status for every identified item and carries at most three clarification questions. The digest stays pending until `scripts/build_assignment_brief_digest.py confirm <digest.json> <human-record.json>` binds an explicit human confirmation record; before that confirmation, present no design analysis, program table, area allocation, option, or spatial recommendation.

## Student Design Start Board

When a confirmed AssignmentBriefDigest exists and the student needs to see the confirmed requirements, conflicts, missing items, and the one next step before any program work, read [student-design-start-board.md](student-design-start-board.md), run `scripts/build_student_design_start_board.py build <confirmed-digest.json> --output <start-board.json>`, then `scripts/build_student_design_start_board.py validate <confirmed-digest.json> <start-board.json>`. The board reads only a confirmed digest and never reinterprets it; it does not replace the normalized brief ledger, and it is not design analysis, a program/area ledger, an option comparison, or a PPTX. The next step it points to is program-and-area work.

## Student Spatial Program

Once a confirmed digest, a validated start board, and a student-authored spatial program draft exist, read [student-spatial-programming.md](student-spatial-programming.md) and use `scripts/build_student_spatial_program.py` to confirm the pending draft with a human record and then build from the confirmed digest, board, and draft. It organizes only what the student wrote, invents no space, area, relation, or design, and emits JSON data only. Its next action is `resolve_program_gaps` or `dimension_candidates`; it is not the normalized brief ledger, design analysis, or a presentation.

## Student Dimension Plan

Once a confirmed spatial program exists and the student has written long-by-short candidates, read [student-dimension-plan.md](student-dimension-plan.md) and use `scripts/build_student_dimension_plan.py` to confirm the pending dimension draft with a human record, then build and validate. Candidates are human-authored and machine-checked only; it selects no candidate and decides no floor count, massing, grid, orientation, coordinate, level, height, or environmental conclusion. Next action `resolve_dimension_gaps` or `human_select_dimension_candidates`; JSON data only, no PPTX, HTML, image, or coordinate drawing.

## Student Floor and Functional Zoning Framework

Once the human has selected one dimension candidate per space and the student has written levels and zones, read [student-floor-zoning-framework.md](student-floor-zoning-framework.md) and use `scripts/build_student_floor_zoning.py` to record the selection, confirm the pending floor zoning draft with a human record, then build and validate. It verifies only the student-written levels, zones, access scopes, activity characters, public-internal boundaries, and unresolved items; it decides no level count, entrance, circulation, coordinate, site plan, massing, grid, elevation, height, or scheme, and recommends, ranks, or selects no zone. Output is JSON data only: no PPTX, image, HTML, or plan drawing.

## Student Circulation and Environmental Intent Framework

Once a confirmed floor zoning framework exists and the student has written circulation and environmental intentions, read [student-circulation-environment-framework.md](student-circulation-environment-framework.md) and use `scripts/build_student_circulation_environment.py` to confirm the pending draft with a human record, then build and validate. It verifies only the student-declared horizontal circulation relations, vertical movement intentions, environmental preferences, and unresolved items; it decides no level count, entrance, core, stair or lift position, orientation, site conclusion, coordinate, plan, massing, grid, elevation, height, or scheme, and recommends, ranks, or selects nothing. Output is JSON data only: no PPTX, HTML, image, or drawing.

## Student Massing, Grid and Height Hypotheses Framework

Once a confirmed circulation-environment framework exists with no unresolved items and the student has written 2–6 massing, grid, and height hypotheses, read [student-massing-grid-height-framework.md](student-massing-grid-height-framework.md) and use `scripts/build_student_massing_grid_height.py` to confirm the pending draft with a human record, then build and validate. It only verifies, accounts, projects, and compares the student-written hypotheses; it never recommends, ranks, or automatically selects any hypothesis; it decides no entrance, plan coordinate, orientation, site conclusion, structural system, regulation, or constructibility. Output is JSON data only: no PPTX, image, HTML, drawing, or three-dimensional model.

## Student Hypothesis Comparison and Human Selection

Once a validated massing-grid-height framework exists and the student has written a comparison draft over its actual hypotheses, read [student-hypothesis-comparison-selection.md](student-hypothesis-comparison-selection.md) and use `scripts/build_student_hypothesis_comparison.py` to confirm the pending draft with a human record, build the pending comparison document, then `validate` it. It projects only the student-written hypotheses, ordered criteria, assessments, and optional guidance, and restates the confirmed upstream facts; it never forces two options, drops or adds a candidate, ranks, scores, or automatically recommends or selects anything, and it decides no floor count, entrance, coordinate, orientation, site plan, massing shape, structural system, regulation, cost, performance, or constructibility. Every projected guidance carries the fixed boundary "This is decision guidance, not an automatic architectural decision." The stage completes only through one explicit human selection record (`SELECT_STUDENT_MASSING_GRID_HEIGHT_HYPOTHESIS`) with a human label, a timezone-qualified RFC 3339 time, exactly one existing candidate key, and the canonical JSON plus newline SHA-256 of the whole pending comparison document; the machine never selects by default, by score, or by accepting a recommendation. Next action `human_select_massing_grid_height_hypothesis` until selected, then `handoff_selected_massing_grid_height_hypothesis`, a controlled handoff to the next separately reviewed stage that does not enter PPTX generation or automatic plan drawing. Output is JSON data only: no PPTX, image, HTML, drawing, or three-dimensional model.

## Student Selected Hypothesis State and Controlled Handoff

Once a selected ARCH-104 comparison document exists, read [student-selected-hypothesis-state-handoff.md](student-selected-hypothesis-state-handoff.md) and use `scripts/build_student_selected_hypothesis_state.py` to build the closed state package from the selected document and its confirmed upstream chain, then `validate` it. It accepts only the `selected` comparison state, reuses the ARCH-104 validate entry for the full ARCH-097~104 chain, and never re-selects, re-ranks, scores, recommends, or derives a design from the selection. The package binds the selected comparison document and the human selection record machine-only, and hands the human a readable selected-hypothesis view plus the controlled next step `author_selected_plan_framework_draft`; it decides no plan coordinate, room rectangle, entrance, total plan, massing shape, orientation, column grid value beyond the written bays, structural system, regulation, cost, performance, or constructibility, and generates no PPTX, image, HTML, drawing, or three-dimensional model. Any upstream change invalidates the handoff and requires rebuild plus revalidation. Output is JSON data only: no PPTX, image, HTML, drawing, or three-dimensional model.

## Student Plan Relationship and Placement Framework

Once a valid selected hypothesis state package exists, read [student-plan-framework.md](student-plan-framework.md) and use `scripts/build_student_plan_framework.py` to confirm the pending plan-framework draft with a human record, build the closed plan framework, then `validate` it. It reuses the ARCH-105 validate entry for the full ARCH-097~105 chain and accepts only a valid, untampered selected hypothesis state package; upstream error codes propagate unchanged and no selection is ever replaced or re-derived. It projects only the student-written plan placements, space relations, movement gradients, and unresolved plan items over the confirmed spaces, levels, and zones; it verifies that every confirmed space is placed or explicitly deferred exactly once, that each placement stays inside its confirmed level and zone, that each relation pair names real, distinct spaces with a unique undirected pair, and that each sequence element is a real space or confirmed zone. It generates no plan coordinate, room rectangle, wall, door, column, entrance, circulation drawing, or total plan, and it decides no orientation, massing shape, structural system, regulation, cost, performance, or constructibility. Next action `resolve_plan_framework_gaps` while unresolved plan items remain, then `human_review_plan_framework`; the machine never fills, resolves, ranks, scores, or recommends anything. Output is JSON data only: no PPTX, image, HTML, drawing, or three-dimensional model.

## Student Schematic Plan Blocks and Local Coordinates

Once a valid ARCH-106 plan framework exists with no unresolved plan items, read [student-schematic-plan-blocks.md](student-schematic-plan-blocks.md) and use `scripts/build_student_schematic_plan_blocks.py` to confirm the pending schematic-plan draft with a human record, build the closed schematic plan blocks, then `validate` it. It reuses the ARCH-106 validate entry for the full ARCH-097~106 chain and accepts only a valid, untampered plan framework without unresolved items; upstream error codes propagate unchanged, and unresolved upstream items fail closed before any output with `SCHEMATIC_PLAN_UPSTREAM_UNRESOLVED`. It verifies only the student-written local containers and placements: every confirmed space is placed exactly once inside its confirmed level, each rectangle stays inside its level container without positive-area overlap, each rotation maps the human-selected long and short sides, declared adjacent pairs share a positive boundary segment, and declared separate pairs stay apart; `near` and buffered relations remain human intent with no fabricated distance judgment. The coordinates are local schematic coordinates only: no site plan, no orientation, no walls, doors, columns, or building outline. Next action `human_review_schematic_plan_blocks`; the machine never moves, optimizes, or draws anything. Output is JSON data only: no PPTX, image, HTML, drawing, or three-dimensional model.

## Student Schematic Plan Review and Controlled State Handoff

Once valid ARCH-107 local schematic blocks exist, read [student-schematic-plan-state-handoff.md](student-schematic-plan-state-handoff.md) and use `scripts/build_student_schematic_plan_state_handoff.py` to build then `validate` a handoff from those blocks and one human review record. The review record binds the whole blocks document, names a human reviewer and timezone-qualified time, and states either `continue_to_handoff` or `revise_schematic_plan`; only the first can produce output. The script reuses the ARCH-107 validation entry for the complete ARCH-097~107 chain, never treats draft confirmation as implicit review, and never alters a rectangle, creates a drawing, selects an option, or applies review notes. It carries local schematic coordinates only and decides no site plan, orientation, wall, door, column, stair, entrance, structure, regulation, cost, performance, constructibility, or PPTX. Output is JSON data only; next action `human_continue_manual_schematic_design` remains human work.

## Student Main Space, Supporting Space, and Sequence Framework

Once a valid ARCH-108 schematic-plan state handoff exists, read [student-main-space-support-framework.md](student-main-space-support-framework.md) and use `scripts/build_student_main_space_support.py` to confirm a student-written organization draft, then build and `validate` the closed framework. The draft gives every space one role: `main_space`, `supporting_space`, or `shared_service`, plus support relationships and any intended spatial sequences; the machine only checks that every handoff space is represented once, every named relation and sequence item is real, and the human confirmation binds the exact pending draft. It does not recommend a main space, move a block, change a coordinate, add a room, resolve a transition, draw a plan, or decide an entrance, corridor, toilet, structure, regulation, cost, performance, or constructibility. Output is JSON data only: no PPTX, image, HTML, drawing, or three-dimensional model. Its next action is `resolve_main_space_support_gaps` when the student records unresolved items, otherwise `human_refine_spatial_sequence`.

## Student Spatial Hierarchy, Openness, Enclosure, and Transition Framework

Once a valid ARCH-109 main-space-support framework exists with no unresolved items, read [student-spatial-transition-framework.md](student-spatial-transition-framework.md) and use `scripts/build_student_spatial_transition.py` to confirm a student-written transition draft, then build and `validate` the closed framework. The inherited human-authored space roles remain the hierarchy; this stage only records one human transition pattern or an explicit unresolved item for each real same-level sequence/support pair: `gradual_opening`, `gradual_enclosure`, `buffered_transition`, `interwoven_access`, or `remain_independent`. It checks source binding and pair coverage only; it does not change a role, choose a pattern, move a block, compute a dimension, create a coordinate, draw a plan, or decide an entrance, corridor, toilet, structure, regulation, cost, performance, or constructibility. Output is JSON data only: no PPTX, image, HTML, drawing, or three-dimensional model.

## Student Spatial Transition Review and Controlled State Handoff

Once a valid ARCH-110 spatial transition framework exists with no unresolved items, read [student-spatial-transition-state-handoff.md](student-spatial-transition-state-handoff.md) and use `scripts/build_student_spatial_transition_state_handoff.py` to build then `validate` a handoff from that framework and one human review record. The review record binds the whole framework by canonical JSON plus newline SHA-256, names a human reviewer and timezone-qualified time under the fixed action `REVIEW_STUDENT_SPATIAL_TRANSITION_FRAMEWORK`, and states either `continue_to_manual_spatial_design` or `revise_spatial_transition`; only the first can produce output. The script reuses the ARCH-110 `validate_spatial_transition_framework` entry for the complete ARCH-097~110 chain, propagates upstream errors unchanged, fails closed on unresolved transition items before any review validation, never treats draft confirmation as implicit review, and never generates, applies, inverts, or completes a review note or transition. It projects only the confirmed human space hierarchy and transition patterns plus the review summary; it creates no coordinate, rectangle, entrance, corridor, wall, door, column, stair, toilet, drawing, plan, site conclusion, structure, regulation, cost, performance, or constructibility claim. Output is JSON data only; next action `human_continue_manual_spatial_design` remains human work.
