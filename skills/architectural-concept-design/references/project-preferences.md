# Confirmed personal preferences within one project

Adapt collaboration, not the general Skill or model. Read only relevant records
in the authorized project for the speaking user. Do not infer their design-user
identity from an account, scan other projects or build a cloud profile.

## Record only an explicit ongoing preference

“From now on, show before/after drawings first and explain briefly” qualifies.
Check existing equivalent records, then adapt
[design-preferences.template.md](../assets/design-preferences.template.md) as
project-local `DESIGN-PREFERENCES.md` when project writes are authorized. Briefly
acknowledge it; do not ask again for the preference just explicitly requested.

Record local entry ID, user-provided applicable name, project scope, concise
preference, explicit instruction basis and active/disabled status. No account
identifier or real name is required. Store no full chat, address, path, secret
or task brief. Repeated patterns/guesses need confirmation before becoming a record.

“Keep this foyer at 28 m²” is a design condition/lock in the design context, not
a personal habit. “This time explain every calculation” is a one-off instruction,
not permission to replace a lasting preference. A preference cannot authorize
bypassing evidence, hard conditions, privacy or publication boundaries.

## Apply, correct, disable and forget

- On later relevant tasks apply only active entries for this project and user,
  without repeatedly printing the file or asking again.
- Current instructions override old preferences. Preferences never override facts,
  hard conditions, design locks, permissions or truthfulness.
- A correction replaces the named outdated entry. Read current bytes before
  editing and again before writing, preserving unrelated/manual text. On concurrent
  changes reread/reconcile; never overwrite the full record from an old copy.
- Disable an entry or all adaptation when requested and cease using it.
- Forget an entry by removing its content/applicability, rather than moving the
  same content into an active history. Honor whole-file deletion; do not rebuild
  it from hidden backups or chat memory.
- Update any Skill-managed preference recovery copy so forgotten content cannot
  reappear. Do not claim to erase host chats or user-owned backups; explain actual
  unresolved external copies when relevant.
- Another teammate's entry is not a team default. Another project has no inherited
  preference unless the user explicitly transfers that particular entry.

Do not automatically submit, sync, train on, publish or write actual preferences
into the installed Skill. Packages contain only empty templates. With no applicable
record use current instructions and normal defaults. Verify real fresh-session
reading, correction, disable/forget and isolation; a file's existence proves none.
