# Architectural Concept Design

Build a provisional, traceable architecture pre-design package. Preserve the human designer as decision-maker; do not claim code compliance, construction feasibility, or professional approval.

## Start

1. For a loose human brief, first read [normalized-brief-ledger.md](references/normalized-brief-ledger.md) and run `scripts/normalize_project_brief.py <brief.json> --output <ledger.json>`. This local-only entry records exactly thirteen brief-field statuses and never creates sources, evidence, or design content; `PROVIDED` is not `VERIFIED`. Then read [brief-and-evidence.md](references/brief-and-evidence.md) and [brief-analysis.md](references/brief-analysis.md). Build the broader brief ledger, classify each evidence claim as `PROVIDED`, `VERIFIED`, `INFERRED`, `ASSUMED`, or `PROPOSED`, surface conflicts and missing information, and ask at most three high-impact questions. Complete the ledger before any site, program, or concept work.
2. Validate or normalize structured input against [input.schema.json](references/input.schema.json). Continue with explicit assumptions if information remains missing.
3. Before any runtime precedent-discovery request, read [source-access-registry.json](references/source-access-registry.json) and [runtime-source-access-gate.md](references/runtime-source-access-gate.md). For a documented API, run `scripts/check_source_access.py <request-plan.json>` locally. For a `controlled_crawl_allowed` source, also read [controlled-crawl-plan.md](references/controlled-crawl-plan.md) and run `scripts/validate_controlled_crawl_plan.py <plan.json>` before any later adapter is allowed to open a page. The plan must match the selected source's exact seed, host, path, field allowlist, and page/depth/delay budgets; a `max_depth: 0` source is seed-only and cannot schedule a child page. For offline-only adapter evaluation, read [controlled-crawl-replay.md](references/controlled-crawl-replay.md) and run `scripts/execute_controlled_crawl_replay.py <plan.json> <replay.json>`; it validates synthetic record/replay data only and does not install or invoke an external runtime. For an installed-runtime dry-run preflight, read [controlled-crawl-runtime-dry-run.md](references/controlled-crawl-runtime-dry-run.md) and run `scripts/prepare_controlled_crawl_runtime_dry_run.py <dry-run-input.json>`; it validates only a local isolated receipt, lock, path boundary, and abstract future invocation plan. For the separately reviewed one-page canary contract, read [controlled-crawl-live-canary.md](references/controlled-crawl-live-canary.md). Read [controlled-crawl4ai-live-transport.md](references/controlled-crawl4ai-live-transport.md) before the production adapter command; it requires an explicit `--execute-live` flag, a current human confirmation, and the same validated plan and runtime dry-run input. The existing `execute_controlled_crawl_live_canary.py` CLI still has no transport and refuses live execution. For an offline audit of a failed live worker, read [crawl4ai-live-worker-health-diagnostic.md](references/crawl4ai-live-worker-health-diagnostic.md) and run `scripts/diagnose_crawl4ai_live_worker_health.py <diagnostic-input.json>`; it only classifies one already-sanitized `{category, stage}` diagnostic and re-runs the ARCH-044 receipt/layout dry-run, always reports `local_probe_not_executed`, and refuses `--execute-local-probe` until a separately reviewed, human-authorized probe exists. For that future probe's execution boundary, read [crawl4ai-local-health-probe.md](references/crawl4ai-local-health-probe.md); its gate CLI `scripts/execute_crawl4ai_local_health_probe.py` ships no runner and refuses by default, while `scripts/execute_crawl4ai_locked_local_health_probe.py` wires only the receipt-validated runtime's exact `.venv/Scripts/python.exe` in isolated `-I` mode to the fixed no-page worker (no shell, PATH lookup, page URL, navigation, or environment injection); both require the independent `--execute-local-probe` flag plus a per-run human confirmation and the ARCH-044 dry-run, and a probe outcome is never a page-access, browser-usability, or canary-authorization claim. Here `html_page_scrape: false` still prohibits generic webpage scraping and raw HTML collection, retention, or output; only the registry's machine-checked rendered-short-text contract may limit the reviewed adapter to named short fields after normal rendering of approved plan pages. A passing local gate or plan is not access permission and never permits raw HTML/scripts/cookies/browser state/media retention, media download, redirects, anti-bot bypass, credentials, login state, custom/random user agents, fallback fetch, or a request outside the exact approved plan.
4. After an approved discovery request yields candidate metadata, read [runtime-candidate-selection.md](references/runtime-candidate-selection.md). Validate the local candidate set with `scripts/validate_runtime_candidates.py <candidate-set.json>` before presenting it. Present exactly six conforming runtime candidates when available; otherwise present the available set with its insufficiency report. Do not transfer precedent operations until the human explicitly selects one to three `RC-xxx` candidates. When six controlled-canary observations were previously materialized as an `RCH-xxx` draft handoff and a human has selected one to three entries, read [runtime-candidate-selection-handoff.md](references/runtime-candidate-selection-handoff.md). Run `scripts/materialize_runtime_candidate_selection_handoff.py build <candidate-handoff.json> <selection-receipt.json>` to bind the selection without inventing project identity, relevance, source/evidence records, or a spatial operation. The resulting `RCSH-xxx` handoff is only a human-authoring bridge; it is not an `RCR-xxx` candidate set and cannot unlock precedent transfer or presentation handoff by itself.
5. Read [site-context-analysis.md](references/site-context-analysis.md) when site observations, interpretations, candidate site constraints, or missing site information are in scope. Complete the site ledger before any site strategy, massing, program, or concept work.
6. Read [program-area-and-circulation.md](references/program-area-and-circulation.md) when program, area, adjacency, zoning, or circulation are in scope. Complete the program-and-area ledger before any grid, core, or concept work.
7. Read [grid-core-height-hypotheses.md](references/grid-core-height-hypotheses.md) when grid, structural-system, core, height, or vertical-circulation hypotheses are in scope.
8. Read [concept-options-and-decisions.md](references/concept-options-and-decisions.md) when extracting precedent operations, creating alternatives, comparing options, or recording a decision. When a user asks to browse or use the local curated precedents, also read [attribution-only-case-cards.json](references/attribution-only-case-cards.json). Treat its summaries as attributed reference prompts, not VERIFIED facts or runtime evidence; do not follow its source links. When a user asks to review the audited note beside one local card, also read [case-research-supplements.md](references/case-research-supplements.md) and its linked data; a supplement never alters the card without human confirmation. When a user asks to present one local card as a visual editorial card, also read [case-card-presentation.md](references/case-card-presentation.md); for a selected local visual, additionally read [case-media-assets.md](references/case-media-assets.md) and its manifest. Never add media to the eight-field card or fetch a source at render time.
9. Read [option-comparison-decision-handoff.md](references/option-comparison-decision-handoff.md) when comparing concept options against criteria, requesting a human design decision, establishing dependency edges, or preparing a stale-propagation handoff.
10. Read [output-contract.md](references/output-contract.md) before producing a package. When a normalized ledger is available, run `scripts/build_normalized_brief_human_assembly_handoff.py <ledger.json> --output <handoff.json>` and present its `UNKNOWN` and `MISSING` todos plus its required human-authored chapters. The handoff is not a direct assembly input and no agent may fill its chapters. A human must author a separate schema-valid brief, first hypotheses, options, criteria, and [human-authored draft declaration](references/human-authored-project-state-draft.md); then run `scripts/validate_human_authored_project_state_draft.py <handoff.json> <declaration.json> <input.json> <assembly-draft.json>`. This local-only gate binds the handoff, checks every human todo resolution, and validates the supplied documents in memory without generating a state package. Only after it succeeds, read [project-state-assembly.md](references/project-state-assembly.md) and run `scripts/assemble_project_state.py <input.json> <assembly-draft.json> --output <state-package.json>`. This local-only helper copies only supplied design content, computes the existing input hash, and keeps `decisions` empty pending a human decision; it never creates a concept, fills missing information, accesses a network, or changes the output contract. Shape machine-readable state to [output.schema.json](references/output.schema.json), then run `scripts/validate_state.py validate <input.json> <output.json>` before delivery. When an explicit upstream change occurs, run `scripts/validate_state.py propagate-stale <input.json> <output.json> <trigger_id> <trigger_change_event> <occurred_at>` and write its stdout to a new output package; never supply a system-clock timestamp or overwrite the validated source package.
11. After a human has selected one to three runtime candidates and the architectural-chain package is available, read [presentation-handoff.md](references/presentation-handoff.md). When a human explicitly directs third-party images, drawings, or PDFs for a noncommercial project deck, also read [user-authorized-presentation-media.md](references/user-authorized-presentation-media.md). Validate only already-present local media records with `scripts/validate_user_authorized_media.py <authorization.json> <manifest.json> <candidate-set.json> --assets-root <per-run-root>`. A passing result is offline validation, not access permission: do not access, download, extract, render, or embed third-party media until the separately reviewed presentation-handoff adaptation exists. Shape the active handoff package to [presentation-handoff.schema.json](references/presentation-handoff.schema.json), then run `scripts/validate_presentation_handoff.py <handoff.json>` locally. This step prepares only a traceable deck framework for the independently installed `ppt-master` Skill; it does not install or invoke that Skill, access a network, download media, or generate a PPTX. If a validated real-project state has exactly one explicit human `D-xxx` selection but no reviewed runtime candidates, do not fabricate `RC`/`RCR` records: read [state-only-presentation-handoff.md](references/state-only-presentation-handoff.md), run `scripts/build_state_only_presentation_handoff.py <input.json> <output.json> --handoff-id <SOH-xxx> --validated-at <RFC3339> --output <handoff.json>`, then `scripts/validate_state_only_presentation_handoff.py <handoff.json>`. This bounded fallback transfers only validated state IDs and team-original diagram intent; it never transfers external precedent or third-party media and does not authorize rendering.
12. For the fixed anonymous end-to-end evaluation, read [presentation-e2e-evaluation.md](references/presentation-e2e-evaluation.md) and run `scripts/evaluate_presentation_e2e.py <input.json> <output.json> <candidate-set.json> <handoff.json>`. If a separately installed, pinned `ppt-master` has already produced a local editable PPTX, supply its installation root and the local PPTX only for read-only structural validation. This step never installs or invokes `ppt-master`, fetches a source, or generates a PPTX.
13. For an explicitly human-confirmed fictional teaching run only, read [synthetic-teaching-presentation-handoff.md](references/synthetic-teaching-presentation-handoff.md). This ADR-0008 route is separate from the real-project handoff: require a validated state package with an explicit human `D-xxx` selection and the three labels `HUMAN_AUTHORIZED_ASSUMPTION`, `DEMO_ONLY`, and `NOT_A_REAL_SITE_OR_BUILDABILITY_CONCLUSION`. Run `scripts/build_synthetic_teaching_presentation_handoff.py <input.json> <output.json> <confirmation.json> --handoff-id <STH-xxx> --validated-at <RFC3339> --output <handoff.json>`, then `scripts/validate_synthetic_teaching_presentation_handoff.py <handoff.json>`. It must never transfer `RC/RCR/SRC/E` records, locators, URLs, third-party media, or `VERIFIED` claims. Only when a separately installed pinned `ppt-master` receipt is already valid, run `scripts/render_synthetic_teaching_pptx.py <handoff.json> --ppt-master-root <root> --output-dir <run-root>` to produce local team-original vector pages and an editable teaching deck. This route does not validate a real project, browse, fetch, install, or activate ADR-0007.

## Explicit external dependency bootstrap

When a human explicitly asks to install the independently maintained presentation Skill or the optional Crawl4AI runtime, read [external-dependency-installation.md](references/external-dependency-installation.md). First run `scripts/bootstrap_external_skills.py --skills-root <target> --dry-run`; include `--runtime-root <separate-target> --include-crawl4ai-runtime` only when the human also wants the isolated crawler runtime in the plan. After a human reviews that plan, the non-dry run must include `--apply-reviewed-plan`. The installer uses the reviewed [external-dependency-lock.json](references/external-dependency-lock.json); it never runs automatically during normal Skill use, never updates to latest, never installs or enables `curl-impersonate`, and never uses the runtime to crawl or render a page.

## Release package and clean installation

When a maintainer prepares or verifies a distributable Skill release, read [release-installation.md](references/release-installation.md). Build the deterministic archive, verify its manifest and hashes, and clean-install it before declaring a release. This workflow packages only this Skill's local runtime; it does not install or invoke external sibling Skills, access a network, create a Git tag, publish a release, or generate a PPTX.

## Verified PPTX release entry

When a generated local PPTX must be published as a final release artifact, read [docs/standards/verified-pptx-release.md](../../docs/standards/verified-pptx-release.md) and run `node scripts/release-verified-pptx.mjs --request <request.json>`. This repository-root compositor is the ONLY local release entry: it first runs the ARCH-089 visual QA evidence gate and then the ARCH-088 final-release integrity gate through direct module imports, binding the release to the visual gate's computed SHA so no caller can supply `qa_evidence`, a hash, or a bypass field. A passing result proves traceable evidence binding and release integrity only; it does not prove visual aesthetics, semantics, licensing, compliance, constructibility, or human review.

## Workflow

1. Create a brief ledger: objectives, users, site, program, constraints, sources, missing information, and assumptions.
2. Translate the site and brief into architectural constraints and opportunities. Keep observations separate from interpretations.
3. Build program, adjacency, zoning, circulation, grid/core, height, and environmental-response hypotheses. Treat each as revisable rather than fixed fact.
4. For every area schedule, use [area-schedule.schema.json](references/area-schedule.schema.json) and run `scripts/check_area_schedule.py`; do not hand-calculate totals.
5. Generate at least two materially different options. Differentiate site strategy, massing, organization, circulation, structure/grid, sequence, or environmental response—not just language, color, material, or facade style.
6. Compare options against explicit criteria, record the designer's decision, and mark downstream artifacts stale if an upstream constraint changes.
7. Deliver a readable report plus a machine-readable state package. Surface evidence labels, sources, assumptions, unresolved questions, and next actions.

## Output minimum

Return:

- a brief and evidence ledger;
- site/program/structure hypotheses and any calculated area summary;
- at least two differentiated concept options;
- an option comparison with a human decision request;
- a traceable state package conforming to [output.schema.json](references/output.schema.json).

## Boundaries

- Treat regulations and project claims as unverified unless their jurisdiction, edition, clause, source, retrieval date, and verification state are recorded.
- Analyze landscape only as an architectural site condition. Do not perform standalone landscape, interior, exhibition, construction-document, or construction structural-calculation work.
- Re-run deterministic checks after changing program quantities, constraints, or scoring inputs.
